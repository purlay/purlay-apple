# Architecture overview

Purlay for Apple platforms is two apps, the iPhone and iPad app and the Mac app, over one engine, in one repository. Both are
clients: they hold no business rule of the server. They draw what the engine models, and the engine speaks the server's contract,
generated from the bundle the server publishes. What is built is stated plainly; what is only planned says so. The reasons are
in [the decisions](../decisions/README.md); the module rules are in [modules-and-layers.md](modules-and-layers.md).

## Goals and constraints

- **One change, one pull request.** The engine, a screen and its tests change together and are checked once, on every platform
  they reach ([ADR 0001](../decisions/0001-one-repository-one-package-one-project.md)).
- **Floors:** iOS 18 and macOS 26, built with the OS 27 SDKs (Xcode 27). Liquid Glass is the primary design; iOS 18–25 get a
  system material in the same shape, behind one availability seam in `PurlayDesign`
  ([ADR 0002](../decisions/0002-platform-floors-and-one-availability-seam.md)).
- **The server's shape is the app's shape.** Purlay is a core plus modules; an app is a core plus one feature module per server
  module, shown only where the server runs it and the workspace may use it
  ([ADR 0003](../decisions/0003-layers-and-feature-modules.md)).
- **The contract has one home,** the server repository; here it is pinned and generated, never written by hand
  ([ADR 0004](../decisions/0004-the-contract-is-the-servers.md)).
- Swift 6 language mode, complete strict concurrency, warnings are errors; `@Observable` and SwiftUI; UIKit or AppKit only where a
  system API asks for it.

## How an app talks to the server

The engine (`PurlayKit`) does this; each app supplies the platform's pieces through `AppEnvironment` (`Apps/iOS/App/Environment/
RealEnvironment.swift`, `Apps/macOS/App/Environment.swift`).

1. **Handshake.** `GET /api/client` (public) returns the server version, the contract version, capabilities and the minimum app
   version. A server the app cannot read, or an app the server no longer serves (`426 CLIENT_TOO_OLD`), is a `ServerProblem`, a
   phase of its own with the reason. Features are switched on by capabilities, never by version; an unknown capability is ignored.
2. **Sign-in, no password in the app.** `ASWebAuthenticationSession` opens the server's sign-in page. After the person approves,
   the page calls `POST /api/native/authorize` (PKCE challenge and state) and the server redirects to `purlay://auth?code&state`
   (the scheme is fixed by the server; `PURLAY_URL_SCHEME` in `Config/Shared.xcconfig`). The app calls `POST /api/native/token`
   with the code, the verifier and the device name, and receives the session as the `__Host-purlay_session` cookie, kept in the
   Keychain and sent on every request and on the WebSocket upgrade. Sessions are listed and revocable per device.
3. **Reads and writes** over HTTP with the generated client and keyset pagination; every error is `{ error: { code, message } }`,
   matched from the generated union. `X-Purlay-Client: ios/<version> contract/<n>` (or `macos/…`) names the platform.
4. **Realtime.** One WebSocket per signed-in session; on reconnect the client replays from its cursors. A send is painted first
   and reconciled after; a failed send stays visible with Retry, and unsent messages survive a relaunch (the outbox).
5. **Server address.** Release builds talk to the hosted address (`ServerAddress.hosted`, purlay.app) over HTTPS with App
   Transport Security strict. Debug builds read `PURLAY_DEV_SERVER` and may use plain HTTP to a local server: the exception is
   written into `Info.plist` by the Debug configuration alone. Entering a self-hosted address is FR-025 (iOS) and Q-007 (Mac).

Not built, and needed before an iOS release: closed-app delivery (APNs: the server speaks Web Push only), a local store for
cold start (A-003), and an `ios` minimum-client gate on the server (Q-003).

## The apps

| | iPhone and iPad | Mac |
|---|---|---|
| Target, scheme | `Purlay iOS`, `Purlay-iOS` | `Purlay macOS`, `Purlay-macOS` |
| Bundle id | `dev.purlay.ios` | `dev.purlay.mac` |
| Screens | `Apps/iOS/App`: one screen per phase of `AppModel`, decided from a pure value (`RootScreen`) | `Sources/PurlayMacUI`, every screen and control; the app target is a shell of scenes, commands and system adapters |
| Design | `PurlayDesign` | `PurlayMacUI`'s `TokenBinding` and `NativePalette`, until it moves onto `PurlayDesign` |
| Sentences | `Apps/iOS/App/Root/Words.swift` and `Apps/iOS/App/Resources/Localizable.xcstrings` | `Sources/PurlayMacUI/Strings.swift` and `Apps/macOS/App/Resources/Localizable.xcstrings` |
| Distribution | none yet (Q-001); `release-ios.yml` makes an unsigned archive | Developer ID, notarized, Sparkle (`Apps/macOS/App/Updates`) |

The Mac app outlives its last window (`applicationShouldTerminateAfterLastWindowClosed` is false), so the socket stays open and a
notice can arrive; work that must survive a closed window starts in the app, not in a view's `.task`.

## The Mac's sandbox and signing

The Mac app is sandboxed. Its entitlements (`Apps/macOS/App/Resources/Purlay.entitlements`) are an allowlist: the sandbox,
outgoing network, user-selected files (read-write), and two mach-lookup exceptions for Sparkle's installer services. Debug adds
only `disable-library-validation`, so the prebuilt Sparkle loads under ad hoc signing. `scripts/enforcement` checks the declared
files and `scripts/verify macos` the signed app against that allowlist. A release is signed with Developer ID and the hardened
runtime, with Sparkle's nested helpers signed first (`scripts/sign-release`); library validation stays on.

## Builds, checks and releases

- `make verify` runs the lanes a pull request needs (`scripts/verify`); CI runs them side by side and one job, `verify`, is the
  required check ([ci.md](../development/ci.md), [ADR 0008](../decisions/0008-ci-lanes-and-one-required-check.md)).
- `scripts/enforcement` holds the rules a compiler cannot state, and `--demo` proves each one refuses its violation
  ([modules-and-layers.md](modules-and-layers.md)).
- Every build is numbered with the commit count (`scripts/build-number`), above build 10, the Mac's 0.3.0.
- Each platform has its own version, tag (`ios/v*`, `macos/v*`), changelog and channel
  ([ADR 0007](../decisions/0007-releases-per-platform.md), [releasing.md](../development/releasing.md)).

## Non-functional requirements in the architecture

| Concern | Where it shows |
|---|---|
| Security | no password in the app; Keychain; PKCE; the Mac's sandbox allowlist; strict ATS in Release; signed and notarized Mac builds; a signed update feed; gitleaks over the history; signing secrets only in a protected environment |
| Privacy | notices carry no message content; local state is scoped by server, account and workspace; signing out lets everything go; the iOS privacy manifest checked against the code |
| Accessibility | labels on every control, Dynamic Type, Reduce Transparency, Increase Contrast and Reduce Motion followed; Liquid Glass can be turned off on the Mac |
| Localization | English and Turkish, one catalogue per app, each checked by a script |
| Offline | the durable outbox and replay from cursors |
| Performance | an idle app holds two timers and makes no request (`IdleBudgetTests`); compilation is cached by content so checks stay fast |
